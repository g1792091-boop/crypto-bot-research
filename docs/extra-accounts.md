# 추가 paper 계좌 (복제 계좌 · 새 매매법 계좌)

두 분이 대시보드에서 승인한 제안으로 **새 paper 계좌**가 원래 계좌(v4: 331개) 옆에서 돕니다. 원래 계좌는 아무것도
바뀌지 않습니다(규칙 5장: 개선은 새 계좌, 원본은 그대로). 코드: `paperbot/extras.py`, `paperbot/newlab_live.py`.
승인 쪽(제안·버튼·회의)은 `docs/agent-rooms.md`에 있습니다.

## 1. 두 종류

| 종류 | 계좌 이름 | 무엇 | 신호 |
|---|---|---|---|
| 복제 계좌 (`copy`) | `N17_KC_RSI@15m~c1` | 36개 매매법 중 하나의 한 봉에 **딱 한 가지**만 바꾼 것: 처음 손절폭 k ATR(`stop_atr` 1.5/2.5/3.0), 첫 익절 잠금(`lock_start` 0.15/0.20/0.30), 특정 차트 특징의 진입 건너뛰기(`skip_tag`, 7개 태그 중 하나) | 원본 계좌(부모)와 같은 신호. 계좌가 시작된 **뒤에** 닫힌 봉의 신호만 받습니다. 건너뛴 신호는 `FILTERED`("규칙으로 건너뜀")로 기록 |
| 새 매매법 계좌 (`newlab`) | `NL1@1h` | 새 매매법 연구실(`docs/newlab-prereg.md`)에서 5년 시험 관문을 통과하고 두 분이 승인한 매매법 | 연구실과 같은 신호 코드(`newlab_signals`)를 같은 차트 봉으로 계산. 청산·크기·비용은 paper v3 그대로(2 ATR 손절, 20~50배 자동, 계단식 익절) |

- 둘 다 **시작 시점에 $5,000**으로, 열린 포지션 없이 시작합니다. 판정(30일 체크포인트)도 **그 계좌가 시작된 날부터** 셉니다.
- 한도: 복제 계좌는 매매법마다 1개, 전체 10개. 새 매매법 계좌는 전체 10개. 지금은 계좌가 도는 동안 자리를 계속 차지합니다(파산해도 풀리지 않음, 열린 질문 Q-1).
- 처음 21일(관찰 기간)에는 제안 자체가 없습니다. 처음 60일의 복제 계좌와 모든 새 매매법 계좌는 두 분의 승인 클릭이 있어야 합니다.
- **paper v4 (2026-10, `docs/paper-v4-rules.md`)**:
  - 복제 계좌의 원본은 **매매법 36개의 15분·30분·1시간·4시간 계좌만** 됩니다. 딥시크(DS200) 44개와 릴스 5분 단타(REEL_H1) 계좌는
    복제하지 않습니다(두 분 결정 D9). 그런 제안은 봇이 영구히 거절합니다(`spec_invalid`, "딥시크·릴스 5분 단타 계좌는 복제 계좌를 만들지 않음(v4 규칙 D9)").
  - 5분봉에는 추가 계좌가 없습니다(v4의 5분봉은 릴스와 그 비교용 동전 3개만). 새 매매법 계좌도 15분·30분·1시간·4시간에서만 시작합니다.
  - 코드가 바뀌어 30일 기간을 다시 세는 일(Q5)은 **그룹마다 따로** 셉니다: 추가 계좌의 코드(`extras.py`, 새 매매법 신호 코드)가 바뀌면 추가 계좌만,
    딥시크 코드가 바뀌면 딥시크 계좌만, 릴스 코드가 바뀌면 릴스와 5분 동전만, 공통 거래 코드가 바뀌면 모두 다시 셉니다(`paperbot/runinfo.py`).

## 2. 계좌가 생기는 순간 (코드가 한 번 더 확인)

두 분이 승인을 누르면 에이전트가 제안을 `approved`로 바꿉니다. 그다음 **5분 봉 경계**(그 경계가 2분 이내로 새것일 때만)에
live 봇이 승인된 제안을 **읽기만** 하고(에이전트 장부 `agents3.db`, 승인 클릭 기록 `inbox.db`) 아래를 모두 다시 확인합니다.
하나라도 아니면 계좌를 만들지 않고 이유 코드를 남깁니다(7장).

1. 이미 만든 제안인지 (같은 제안 번호와 같은 작성 시각이면 건너뜀)
2. 제안의 계좌 정의가 시험 장부와 맞는지, 규칙이 허용 목록 안인지 (코드가 직접 확인, AI 글은 읽지 않음)
3. 시험 장부 상태 (복제: `passed`, 새 매매법: `proposed`)
4. 이번 paper 운영 중의 제안인지 (관찰 기간 뒤에 쓰였는지)
5. 두 분의 거절 클릭이 없는지 (한 번이라도 있으면 만들지 않음)
6. 두 분 승인이 필요한 제안이면 두 분의 결정이고 대시보드 승인 클릭이 실제로 있는지
7. 이 기능이 켜지기 전에 승인된 것이면 그 뒤에 승인 클릭이 한 번 더 있는지("다시 승인")
8. 같은 계좌가 이미 없는지
9. 복제: 원본 계좌가 있고, 파산하지 않았고, `paper3.db`에 닫힌 거래가 30건 이상인지
10. 관문을 **지금의 시험 수**로 다시 판정해도 통과하는지 (장부 개수는 직접 세고, 한 번 본 최대값 아래로는 내려가지 않음, 에이전트 쪽 계산과도 맞춰 봄)
11. 한도
12. 새 매매법: 신호 코드를 쓸 수 있고 기록이 충분한지

통과하면 그 경계 시각을 시작 시각으로 계좌가 만들어지고, 바로 다음 1분봉부터 돕니다. 텔레그램(무음)
`[extra] 새 paper 계좌 시작: … (계좌 이름), 제안 #번호`이 오고, 에이전트 방에 "계좌가 시작됐습니다"가 올라옵니다.
계좌 이름은 봇이 정합니다(복제는 `…~c번호`, 새 매매법은 `NL번호`, 번호는 이 `paper3.db` 안에서 다시 쓰지 않음).

**시작된 계좌는 거절로 멈출 수 없습니다.** 원본을 바꾸지 않는 것과 같은 이유로 계좌의 규칙도 바뀌지 않습니다. 대시보드에서
거절을 누르면 "이미 시작된 계좌입니다"가 나옵니다.

## 3. 도는 방식 (원래 계좌에 영향이 없게)

- 5분 경계마다 원래 계좌의 신호 계산·기록·주문 대기·저장이 **먼저 끝나고 저장된 뒤에** 추가 계좌 처리가 따로 저장됩니다.
  추가 계좌 처리가 실패하면 그 처리만 되돌리고 경고를 남깁니다(원래 계좌는 그대로 이어서 돕니다).
- 재시작 직후 밀린 1분봉을 따라잡는 동안에는 새 매매법 신호 계산과 새 계좌 만들기를 하지 않습니다(그때 계산하면 원래 계좌의
  다음 신호가 늦어질 수 있음). 그 봉들의 개수는 기록되고, 판정 때 신호 비율에서 빠집니다.
- 새 매매법 신호 계산에는 시간 예산(기본 20초)이 있습니다. 넘으면 남은 계산을 건너뛰고 경고합니다. 10개 계좌(4시간봉 4개)
  기준 약 3초입니다.
- 추가 계좌의 경고(낙폭·파산)는 원래 알림 모음과 따로 **"추가 계좌 알림 모음"**(한 시간에 한 번, 무음)으로 옵니다.
  강제청산·정지 같은 CRITICAL은 알림 목록에는 바로 적히고, 텔레그램으로는 그 처리(한 번 받은 1분봉 묶음)가 끝난 뒤나 다음
  새 5분 경계의 추가 계좌 처리 뒤에 한 메시지로 옵니다(여러 개면 묶어서). 텔레그램 전송은 몇 초씩 걸릴 수 있어, 원래 계좌의
  다음 신호 계산 앞에서는 보내지 않습니다. 따라잡는 중의 지난 경계에서는 알림 모음도 보내지 않습니다.
- 체결 비용 기록(호가창으로 계산한 실제 체결 비용, `fill_costs`)은 원래 계좌의 진입·청산에서만 호가창을 새로 받습니다.
  추가 계좌의 진입·청산은 같은 1분에 원래 계좌를 위해 받은 호가창이 있으면 그것으로 계산하고, 없으면 `skipped`로 남깁니다
  (호가창 요청은 그 경계의 원래 계좌 신호 계산 전에 돌아 기준 가격·시각을 늦출 수 있음).

## 4. 멈춤과 정지 (봇이 스스로 하는 안전 조치)

| 상태 | 언제 | 무엇 |
|---|---|---|
| 정상 (active) | | 신호를 받고 거래 |
| 멈춤 (suspended) | 새 매매법 계좌의 규칙을 읽을 수 없거나, **신호 코드가 바뀌었을 때**(`newlab_signals.py`, `context.py`, `recorder.py`, 잠긴 라이브러리), 신호 코드를 불러오지 못할 때 | 새 진입 없음. 열린 포지션은 저장된 손절·잠금대로 관리 |
| 정지 (held) | 복제 계좌의 규칙을 읽을 수 없을 때, 계좌 계산 중 오류가 났을 때 | 저장된 상태 그대로 얼림(손절 확인도 하지 않음) |

바뀔 때마다 CRITICAL 텔레그램 `[extra] 계좌이름: …`과 기록이 남고, 체크포인트 판정에 "추가 계좌만 해당"으로 표시됩니다.
원인이 없어지면(코드 복구) 다음 재시작 때 다시 정상으로 돕니다.

**신호 코드가 바뀌어 멈춘 새 매매법 계좌를 계속 돌리려면** 두 분이 바뀐 코드를 받아들인다는 뜻으로 알림에 나온 코드 값을
`extras.json`의 `accept_code`에 넣고 봇을 재시작합니다(`"accept_code": {"NL1@1h": "1a2b...-9f8e...-..."}`).
이것은 그 계좌만의 Q5 사건으로 기록됩니다(그 계좌의 30일 기간을 그날부터 다시 셈).

## 5. 설정 (`/etc/paperbot/extras.json`, 없어도 됨)

예시와 설명: `deploy/extras.example.json`. 파일이 없으면 기본값으로 돕니다. 봇은 5분 경계마다 파일이 바뀌었는지 보고
다시 읽습니다(재시작 필요 없음, `accept_code`만 재시작 때 적용). 파일이 깨졌으면 이전 설정을 그대로 쓰고 경고합니다.

| 키 | 기본 | 뜻 |
|---|---|---|
| `agents_db`, `inbox_db` | `paper3.db` 옆의 `agents3.db`, `inbox.db` | 둘 중 하나만 쓰면 새 계좌 만들기를 끄고 경고 (도는 계좌는 계속) |
| `observe_days` | 21 | 관찰 기간. 21보다 작게 할 수 없음 (3650보다 크면 3650으로 읽음) |
| `observe_until` | 없음 | 관찰 기간을 이 날짜(한국 날짜, 그날 포함)까지 늘림 |
| `owner_ok_days` | 60 | 이 기간에 결정된 복제 제안은 두 분 승인이 필요. 60보다 작게 할 수 없음 (3650보다 크면 3650) |
| `budget_s` | 20 | 새 매매법 계산의 시간 예산(초) |
| `pause_activation` | false | true면 새 계좌를 만들지 않음 (복원 작업 때) |
| `agents_ack` | 없음 | 에이전트 장부가 예전 것으로 바뀐 것을 확인했다는 표시 (6장) |
| `inbox_ack` | 없음 | 승인 클릭 기록(inbox.db)이 예전 것으로 바뀐 것을 확인했다는 표시 (6장) |
| `accept_code` | {} | 4장 |

## 6. 복원 (백업에서 되돌릴 때)

- **agents3.db 또는 inbox.db**: live 봇을 멈추지 않습니다. ① `extras.json`에 `"pause_activation": true` ② 평소의 복원 절차
  (`docs/agent-rooms.md`) ③ inbox.db를 되살렸으면 **백업 뒤에 누른 승인·거절을 두 분이 대시보드에서 다시 누릅니다**(그 클릭은
  백업에 없음) ④ 대시보드나 `status` 명령에 `agents_db: regressed`가 나오면 알림에 나온 값을 그대로
  `"agents_ack": "trial:…/proposal:…"`로, `inbox_db: regressed`가 나오면 `"inbox_ack": "approval:…@…"`로 넣음
  ⑤ `pause_activation`을 false로. 봇은 예전 장부의 같은 번호를 다른 제안으로 착각하지 않습니다(계좌는 제안 번호와 작성 시각,
  시험 번호와 시각, 규칙 내용으로 알아봄). 관문 판정에 쓰는 시험 수는 복원 뒤에도 전에 본 최대값 아래로 내려가지 않습니다:
  봇은 5분 경계마다 모든 방의 시험 수를 세어 두고(아직 승인된 제안이 없는 방도), 관찰 기간(처음 21일)에도 장부의 지문과 시험
  수는 읽어 둡니다. inbox.db가 예전 것으로 바뀐 것도 마지막 승인·거절 클릭의 번호와 시각으로 알아보고, 확인(`inbox_ack`) 전에는
  어떤 계좌도 만들지 않습니다(잃은 거절 클릭 때문에 계좌가 시작되지 않게). 승인 클릭을 잃은 제안은 `owner_click_missing`(기다림)으로
  남고 닫히지 않습니다: 승인한 분이 대시보드에서 "다시 승인"을 누르면 시작합니다.
- **paper3.db**: 지금처럼 live 봇을 멈추고 복원합니다. 백업 뒤에 생긴 추가 계좌는 거래와 함께 사라지고, 그 제안은 다시
  확인되어 새 시작 시각으로 다시 만들어질 수 있습니다(판정 기간도 새로 셈).

## 7. 만들지 않은 이유 코드

봇은 `paper3.db`의 상태 `extras`(`refused`)에 승인됐지만 계좌가 없는 제안의 이유를 남깁니다. "영구"인 것은 제안 상태가 바뀌어야만
풀리므로 에이전트가 제안을 닫습니다. 새 이유가 생길 때 한 번 알림(영구·`id_conflict`는 경고, 나머지는 기록만).

| 코드 | 뜻 | 영구 | 누가 |
|---|---|---|---|
| `contract_missing` | 제안에 계좌 정의가 없음(예전 형식) | 예 | 에이전트가 닫음 |
| `contract_mismatch` | 계좌 정의가 시험 장부·제안과 다름 | 예 | 에이전트가 닫음 (코드 문제) |
| `spec_invalid` | 규칙이 허용 목록 밖 | 예 | 에이전트가 닫음 |
| `trial_status` | 시험 장부가 없거나 상태가 맞지 않음 | 예 | 에이전트가 고치거나 닫음 |
| `stale_run` | 이번 운영 전의 제안, 또는 관찰 기간 중에 쓰인 제안 | 예 | 에이전트가 닫음 |
| `owner_ok_missing` | 두 분 승인이 필요한데 두 분 결정이 아님 | 예 | 에이전트가 닫음 |
| `owner_click_missing` | 두 분 결정인데 승인 클릭 기록이 없음(예: inbox.db 복원) | 아니오 | 승인한 분이 "다시 승인" (크게 알림) |
| `duplicate` | 같은 계좌가 이미 있음 | 예 | 에이전트가 닫음 |
| `gate_now_fail` | 지금의 시험 수로 다시 판정하면 관문 미통과 | 예 | 에이전트가 닫음 |

## 9. 주문 실행기와 추가 계좌

실거래 주문 실행기(`paperbot/executor.py`)는 **아직 추가 계좌를 거부하지 않습니다.** 기본 방식(`entry_source: "paper"`)은
`executor.json`의 `account`가 가리키는 paper 계좌의 포지션을 그대로 따라가므로, `S@15m~c1`(복제)이나 `NL1@1h`(새 매매법)를 적으면
실시간 안전 검토를 거치지 않은 규칙으로 실제 돈을 거래하게 됩니다(신호 방식도 `NL1@1h`는 그대로 맞음). 그러니 **실행기에는 원래
매매법 계좌(`V45_AMB@15m` 같은 것)만 적습니다.** `python -m paperbot.launchcheck`가 `executor.json`의 계좌를 paper3.db에서 찾아
원래 매매법 계좌(`kind = 'strategy'`)가 아니면 [고칠 것]으로 알립니다. 실행기 작업에는 `kind != 'strategy'`인 계좌를 스스로
거부하도록 요청해 두었습니다.

## 10. 원래 계좌가 그대로라는 증명

`tests/extras_harness.py`가 같은 합성 시세(26시간, 7개 코인, 거래 정지 1시간 포함), 같은 시계, 같은 강제 종료 지점으로
기능 전 코드와 지금 코드를 돌려 195개 계좌(시험 세계는 golden 파일을 만든 때의 5개 봉 계좌 그대로입니다. paper v4의 실제 봇은 331개(docs/paper-v4-rules.md)지만, 추가 계좌와 떨어져 있다는 증명은 봉 구성과 상관없음)의 거래·결과·자산 기록·알림·매 처리 뒤 엔진 상태·하루 스냅샷·신호 기록을 해시로
비교합니다(`tests/data/extras_parity_golden.json`은 기능 전 코드에서 만든 것). 추가 계좌가 없을 때, 13개가 돌 때, 재시작, 밀린
분봉 따라잡기, 추가 계좌 처리 중 강제 종료 6곳에서 모두 같아야 테스트가 통과합니다(`tests/test_extras_parity.py`).
1분봉 처리 안의 시간도 봅니다: 호가창 요청(0.3초)과 텔레그램 전송(2초)에 시계 시간을 매긴 실행에서도 추가 계좌가 있든
없든 195개가 같아야 하고, 예전처럼 추가 계좌의 진입·청산이 호가창을 받게 하면 달라지는 것(음성 대조)도 확인합니다.
