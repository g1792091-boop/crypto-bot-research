# 추세 사냥 모의 봇 (huntbot) — 두 분이 하실 일

> 종이 매매만 합니다. 거래소 키가 없고 주문 코드도 없습니다. 바이낸스 공개 시세만 읽습니다.
> 규칙봇·후보 리그와 다른 **새 서버(hunt-judge)** 에서 돌고, 화면·텔레그램도 따로입니다.

## 1. 이게 무엇이고, 왜 지금 켜나요

- 추세 사냥 백테스트(사전 등록 v1 + 넓게)에 들어가는 **모든 시스템(지금 762개)** 을 **2026-10-01부터** 같은 규칙으로
  종이 매매합니다. 각 시스템마다 $5,000 지갑 하나, 위험 0.5%, 백테스트와 **같은 코드**(research/hunt/hunt.py)로 계산합니다.
- 백테스트 결과(픽)는 고정(10/12쯤) 뒤 빌린 서버에서 몇 시간이면 나옵니다. **그때까지 기다리지 않습니다.** 지금 켜 두면
  픽이 정해지는 순간 그 픽의 10/01부터의 기록이 이미 있고, 그 계좌들(라인업)이 화면 맨 앞에 나오고 텔레그램이 시작됩니다.
  10/16에 시작하는 대신 **오늘 켜서 10/01부터의 기록을 바로 갖는** 방식입니다.
- 계산 방식: 5분봉이 닫힐 때마다 10/01부터 지금까지를 처음부터 다시 계산합니다(백테스트와 똑같이). 그래서 백테스트와
  숫자가 어긋날 수가 없고, 자료가 제때 들어오는 한 이미 닫힌 거래가 나중에 바뀌지 않습니다(테스트로 확인했습니다).
- 예외 하나: 어떤 코인의 5분봉이 거래소 사정으로 10분 넘게 늦으면 엔진은 기다리지 않고 나머지 코인으로 계속 계산합니다.
  늦은 봉이 들어오면 그 시간을 다시 계산하는데, 지갑 크기가 모든 코인에 걸려 있어서 그사이 닫힌 다른 거래의 숫자가
  조금 바뀔 수 있습니다. 그런 거래는 **"나중에 바뀐 거래"** 로 처음 본 것과 바뀐 것을 모두 기록하고, 대시보드 '상태'와
  텔레그램(라인업 계좌일 때)에 알립니다. 조용히 바뀌는 일은 없습니다.

## 2. 서버 만들기 (Vultr, 5분)

1. Vultr → **Deploy +** → **Cloud Compute**.
2. 종류: **CPU Optimized** (두 분 말씀대로 비싼 쪽이 빠릅니다). 크기: **32 vCPU** 를 권합니다 (없으면 16 vCPU).
   - 계산 시간(가짜 시세로 잰 값, 762개 시스템, 코인 22개로 환산):

     | 서버 | 보통 5분 | 15분봉 마감 | 4시간봉 마감 (가장 무거움) |
     |---|---|---|---|
     | 4 vCPU (최소: 16 GB, 160 GB) | 약 15초 | 약 3분 | 약 6분 |
     | 16 vCPU | 약 5초 | 약 45초 | 약 1분 20초 |
     | 32 vCPU (권장) | 약 5초 | 약 25초 | 약 45초 |

   - 서버가 작아도 **결과 숫자는 똑같습니다** (지난 봉을 다시 계산하는 방식이라 늦게 계산해도 같은 결과). 화면과 텔레그램이
     그만큼 늦게 바뀔 뿐입니다. 라인업 계좌는 늘 먼저 계산해서 몇 초 안에 나옵니다.
3. 지역: **Tokyo**. 운영체제: **Ubuntu 24.04 LTS x64**.
4. Hostname(이름): **hunt-judge**. 자동 백업은 켜도 되고 꺼도 됩니다.
5. **Deploy Now** → 1~2분 뒤 IP와 root 비밀번호가 나옵니다.

## 3. 한 줄 붙여 넣기 (설치, 1번만)

Termius(또는 Vultr 화면의 콘솔)로 `root@서버IP`에 접속한 뒤, 개발자가 준 **커밋 번호**를 `COMMIT_HERE` 자리에 넣어 이 한 줄을
붙여 넣고 엔터:

```
apt-get -o DPkg::Lock::Timeout=600 update -y && apt-get -o DPkg::Lock::Timeout=600 install -y git && git clone -q -b claude/keen-pasteur-wav02u https://github.com/g1792091-boop/crypto-bot-research.git /root/huntbot-src && git -C /root/huntbot-src checkout -q COMMIT_HERE && bash /root/huntbot-src/deploy/huntbot/install_huntbot.sh
```

- 5~10분 걸립니다. 마지막에 `selfcheck ok` 와 `끝.` 이 나오면 성공입니다.
- 새 서버는 처음 몇 분 동안 스스로 업데이트를 합니다. 그동안은 명령이 최대 10분까지 조용히 기다릴 수 있습니다(정상).
  그래도 `Could not get lock` 이 나오면 5~10분 기다렸다가 **같은 줄을 다시** 붙여 넣으세요.
- 설치가 끝나면 **자료 받기**가 저절로 시작됩니다(2025-01-01부터의 5분봉 22개 코인, 30~40분). 코인 하나를 받을 때마다
  저장하므로 중간에 서버가 재시작돼도 받은 데까지는 남고 이어서 받습니다. 진행은 `journalctl -u huntbot-feed -f` 에서
  코인별로 보입니다. 모든 코인의 과거 자료가 빠짐없이 모인 뒤에야 엔진이 10/01부터 계산을 시작합니다.

그다음 설정 한 번:

```
bash /root/huntbot-src/deploy/huntbot/setup_env.sh
```

   승인합니다. (대시보드는 Tailscale로만 열립니다. 인터넷에는 열리지 않습니다.)

3. **텔레그램**: 규칙봇·후보 리그에서 쓰는 봇 토큰을 그대로 붙여 넣어도 됩니다(안 보이는 게 정상). 받을 대화방 번호를 넣으면

## 5. 픽이 나오면 (라인업 넣기)

- 개발자(메인 세션)가 픽과 결과(통과 = **정식**, 통과 못 함이지만 지켜볼 것 = **참고**)로 `huntbot/lineup.json` 을 채워
  커밋하고 새 커밋 번호를 드립니다. 서버에서 업데이트 한 줄(6장)을 실행하면 끝입니다.
- 정식: 사전 등록 15장대로 위험 0.5%와 1% 두 계좌, 통과가 2개 이상이면 한 지갑 바구니도. 참고: 0.5% 한 계좌.
  목표 모드(2%·5%)는 "참고 읽기"로만 붙습니다(통과 조건 아님).
- 라인업이 바뀌면 그 계좌들의 10/01부터 기록이 바로 화면에 나오고, 텔레그램은 "라인업" 메시지 1개를 보낸 뒤 **그때부터**의
  진입·추가·청산만 보냅니다(지난 거래를 한꺼번에 보내지 않습니다). 전체 기록은 라인업과 상관없이 계속됩니다.

## 6. 업데이트 (개발자가 새 커밋을 주면)

```
git -C /root/huntbot-src fetch -q && git -C /root/huntbot-src checkout -q 새커밋번호 && bash /root/huntbot-src/deploy/huntbot/install_huntbot.sh
```

- 새 코드를 미리 검사(selfcheck)하고 통과할 때만 바꿉니다. 실패하면 아무것도 안 바뀝니다 → 화면을 개발자에게 보내 주세요.
- 엔진 코드가 바뀌면 10/01부터 새 코드로 다시 계산합니다. 예전에 본 거래와 신호는 지우지 않고 그대로 보관합니다
  (`run.db` 의 trades_seen, `events.db` 의 세대). **백테스트 고정(10/12쯤) 뒤에는 고정된 커밋으로 한 번 꼭 업데이트**합니다.

2. 대시보드 오른쪽 위 점이 초록인지.

   뜻입니다(신호 하나는 한 번만 셉니다. 기록은 처음 본 대로 둡니다). 개발자에게 알려 주세요.
4. **상태** 화면의 "나중에 바뀐 거래" 가 "없음"인지. 숫자가 있으면 늦게 들어온 과거 자료(멈췄던 코인의 5분봉, 늦은 펀딩,
   코인 거래 종료) 때문에 이미 닫힌 거래를 다시 계산했다는 뜻입니다. 처음 본 것과 바뀐 것이 모두 남습니다. 드물게
   생기는 일이고 결과 숫자는 백테스트와 같은 쪽으로 맞춰진 것입니다. 자주 늘면 개발자에게 알려 주세요.
5. 텔레그램 "⚠ 자료 지연" 이 오면 서버나 바이낸스 연결 문제입니다. 바이낸스 5분봉이 30분 넘게 늦거나, 자료 수집
   (huntbot-feed)이 30분 넘게 아무 소식이 없을 때 옵니다(엔진이 계산을 못 하고 있어도 옵니다). 다시 들어오면
   "✅ 자료 다시 들어옴" 이 옵니다. 30분 넘게 계속되면 아래 명령 결과를 개발자에게.

## 8. 멈추기 · 다시 켜기 · 지우기

```
systemctl stop huntbot-run huntbot-feed huntbot-dash          # 멈추기 (기록은 남음)
systemctl start huntbot-feed huntbot-run huntbot-dash         # 다시 켜기 (멈춘 동안의 봉도 받아서 이어 계산)
systemctl status huntbot-feed huntbot-run huntbot-dash --no-pager    # 상태
journalctl -u huntbot-run -n 50 --no-pager                    # 엔진 기록 (문제 생기면 이 화면을 개발자에게)
journalctl -u huntbot-feed -n 50 --no-pager                   # 자료 수집 기록
```

- 어떤 코인이 잘못 "거래 종료"로 표시됐을 때(개발자가 말해 줄 때만), 그 코인을 다시 받게 하는 명령(예: XRP):

```
sudo -u huntbot bash -c 'set -a; . /etc/huntbot/huntbot.env; /opt/huntbot/venv/bin/python -m huntbot feed coin-reset XRPUSDT'
```

- 서버를 없애기 전에: `/var/lib/huntbot/events.db`, `/var/lib/huntbot/run.db` 를 받아 두면 기록이 남습니다
  (5분봉 `store.db` 는 다시 받을 수 있습니다).
- 서버 삭제: Vultr → 서버 → **Destroy**.

## 9. 알아 둘 것

- 기록은 **10/01 00:00 UTC (한국 09:00)** 부터입니다. 지표(장세 판단, ATR 등)를 위해 2025-01-01부터의 과거 5분봉을 씁니다.
- 코인은 사전 등록 3장의 30개 중 **지금도 거래되는 22개**입니다(새로 상장된 코인은 넣지 않음). 거래가 멈춘 코인은 빠지고,
  계산 중에 멈추면 그 코인의 포지션은 거래량이 있던 마지막 봉에서 닫힙니다(사전 등록과 같음).
  - "거래 종료"는 한 번 읽은 거래소 상태로 정하지 않습니다. 1시간마다 읽는 상태가 **4번 연속(3시간 넘게)** 거래 중이
    아니고 그동안 새 5분봉이 하나도 없을 때만 정합니다. 그동안에도 그 코인의 봉은 계속 받습니다.
  - 이상한 응답(코인 목록이 비었거나 BTC가 없거나 지난번보다 코인 수가 절반 넘게 적음)은 무시합니다.
  - 종료로 정한 뒤 24시간 안에 다시 거래되면 종료를 되돌리고 이어서 받습니다(그 사이 거래는 다시 계산되고 "나중에 바뀐
    거래"로 남습니다). 그보다 늦으면 개발자 판단으로 위 `coin-reset` 명령을 씁니다.
- 대시보드는 `/var/lib/huntbot/snap` 폴더만 볼 수 있습니다. 5분봉·기록 데이터베이스, 딥시크 금액이 있는 private 폴더,
  텔레그램 토큰이 있는 설정 파일은 대시보드 프로그램에서 아예 보이지 않습니다.
- 이 서버에 복사되는 코드에는 주문 코드가 없습니다. 규칙봇 코드는 장세 판단에 쓰는 파일 15개만 복사하고, 설치할 때
  복사본에 주문·키 관련 코드가 있으면 설치를 멈춥니다.
- 체결은 "신호 봉이 닫힌 다음 5분봉의 시가"입니다. 그래서 화면은 늘 1~2분 늦게 따라옵니다(실제 주문이 없으니 결과는 같습니다).
- AI 판단(hunt judge)은 **아직 만들지 않았습니다.** 나중에 붙일 수 있도록 모든 신호(장세 문에 막힌 것 포함)를
  `/var/lib/huntbot/events.db` 에 기록해 둡니다.
- 백테스트 코드가 아직 고쳐지는 중이라, 고정 전 커밋으로 설치하면 고정 뒤 한 번 더 업데이트해야 합니다(6장).
