# 신호 기록 모드 (경우 B)

작성: 2026-09-30 (KST)

## 왜 이 모드인가
백테스트 세션의 전체 백테스트(매매법 37개 × 봉 6개 × 코인 7개) 결과, 사전 기준을 통과한 "매매법 × 봉"이 **0개**였습니다(인수인계 v2, `SWEEP_RESULTS_KO.md`). 분류는 ① 매매 0칸, ② 기록만 164칸, ③ 제외 58칸입니다.
- 이 분류를 결과 파일로 **다시 계산해 확인**했습니다: 222칸 중 차이 0.
- 인수인계 4.3(경우 B)에 따라 paper 봇은 **"신호 기록 + 실행 인프라 시험"** 모드로 돕니다. 매매하는 매매법은 없습니다.
- ② 칸은 고정 판정일 **2027-04-01, 2027-10-01**에만, 기록된 봉으로 백테스트 세션의 잠긴 코드를 돌려 판정합니다. 매일·매주 성적으로 판단하지 않습니다.

## 두 분 결정 (2026-09-30)
- 두 분 규칙 장부는 **계단 규칙(20%×20배 / 30%×30배 / 40%×50배)을 그대로** 씁니다. 인수인계 문서는 "좋은 자리 점수가 검증되기 전까지 20배×20% 고정"을 권했지만, 두 분이 계단 규칙을 유지하기로 했습니다.
- **XRP는 기록만** 합니다(매매 안 함). ② 재판정 기준이 7개 코인이기 때문입니다.
- 신호 기록 모드 시작.

- 봉은 거래소 시계로 **닫힌 봉만** 저장하고, 한 번 저장하면 고치지 않습니다. 거래소가 나중에 다른 값을 주면 원래 값은 그대로 두고 `revisions`에 따로 남깁니다.
- 데이터베이스마다 쓰는 프로세스는 하나입니다 (인수인계 5.3: 과거 SQLite 사고 재발 방지). `paper.db` = 실시간 봇, `market.db` = 기록기, `agents.db` = 에이전트 점검.

**신호 한 건마다 남는 것:** 신호 ID, 매매법·봉·코인·방향, 신호 봉 시각·종가, ATR14(백테스트 코드의 `fg.atr`), 가상 진입가 = 다음 봉 시가 × (1 ± 0.02%), 신호 봉 종가 → 다음 봉 시가 지연, 신호 직후 호가 기준 체결 추정가(매수는 매도호가, 매도는 매수호가), 기록 시각, 실행 ID.

**기록하지 않는 것:** 청산 결과와 수익. 판정일에 저장된 봉으로 백테스트 코드를 돌려 4·16·64봉 이동과 청산 5종을 한꺼번에 계산합니다(인수인계 5.2).

## 신호 계산 방법
1. 백테스트 세션의 신호 코드(`sweep_lib.py`와 vendor 8개 파일)를 **바이트 그대로 복사**해 `third_party/sweep/`에 두었습니다. 출처는 커밋 `a20ebe5`입니다. 봇은 이 코드를 **다시 짜지 않고 그대로 불러 씁니다** (인수인계 8절).
2. 실행할 때마다 11개 파일의 해시를 `PREREG.sha256`과 대조합니다. 하나라도 다르면 **실행을 거부**합니다.
3. 5분봉 → 15분·30분·1시간·4시간·일봉은 백테스트와 같은 `resample_ohlcv`로 만듭니다. 이 함수는 **아직 안 끝난 봉**을 남기므로, 기록기가 그 봉을 버립니다.
4. `compute_signals`를 백테스트의 판정 실행과 똑같이 호출합니다(상위 시간봉 틀을 따로 넘기지 않음). 워밍업(5분 8,640봉, 15분 2,880, 30분 1,440, 1시간 720, 4시간 300, 일봉 200) 안의 신호는 기록하지 않습니다.
5. 코인마다 **고정 시작점(앵커)** 부터 매번 전체를 다시 계산합니다. 앵커는 처음 저장된 봉이며 옮기지 않습니다.
6. 같은 봉에 롱·숏이 동시에 나오면 숏을 버립니다 (백테스트 코드가 처리).

## 매 실행마다 하는 일관성 검사
전체를 다시 계산해서, 이미 기록된 신호와 비교합니다. 하나라도 다르면 **텔레그램 치명 알림**을 보냅니다.
- **사라짐**: 기록된 신호가 다시 계산하니 안 나옴
- **방향 바뀜**: 같은 봉의 신호 방향이 달라짐
- **뒤늦게 나타남**: 지난 실행 때 이미 진입 봉까지 있었는데 그때는 없던 신호가 새로 나옴

원인 후보는 세 가지입니다: 거래소의 과거 값 수정, 코드 변경, 누락됐던 봉이 뒤늦게 채워짐. 에이전트 저녁 점검의 운영 감사관이 매일 이 결과를 봅니다.

## 재현 시험 상태 (인수인계 5.1)
| 단계 | 내용 | 상태 |
|---|---|---|
| 1. 코드 동일성 | 봇의 기록 결과 = 같은 봉에 잠긴 코드를 직접 돌린 결과 | **가짜 가격 데이터로 통과**: 97칸 6,514건 중 차이 0. 예외는 마지막 봉 신호 2건으로, 진입 봉이 아직 없어 다음 실행으로 미뤄진 것 |
| 2. 실시간 경로 동일성 | 봉이 나눠서 도착해도 한 번에 계산한 결과와 같은가 | **가짜 데이터로 통과**: 4번에 나눠 기록한 결과 = 한 번에 기록한 결과 (시험 코드) |
| 3. 데이터 차이 | Astral 대 바이낸스 신호 일치율 | 아직 안 함. 백테스트 세션의 Astral 원자료가 필요 (기록만 하는 항목, 판정 아님) |

실제 바이낸스 데이터로 하는 1·2단계 확인은 서버에서 합니다. 매 실행의 일관성 검사가 매일 2단계를 다시 확인하는 셈입니다.

## 실제로 돌려 본 결과 (가짜 가격, 이 작업 환경)
- 7개 코인 × 32일치 5분봉: 기록기 **35초**(코인당 약 4.5초), 신호 6,723건, 오류 0. 4시간·일봉 칸은 워밍업 중이라 아직 계산되지 않았습니다.
- 에이전트 저녁 점검 6명이 이 기록을 보고 실제로 점검했습니다: 82초, 약 5.8만 토큰, 근거 검사에서 버려진 주장 0개.
  - "거래 0건은 기록 전용 모드의 정상 상태"로 판단했습니다.
  - ② 신호의 수익은 평가하지 않았습니다.
  - 일부러 빼 둔 호가 스냅샷(12시간치만 있음, 신호의 약 25%만 추정가 있음)을 찾아냈습니다.
- 수정한 것: 에이전트가 "봇 버전 ≠ 잠긴 코드 출처 커밋"을 문제로 오해했습니다. 둘은 원래 다른 값이라 패킷에 설명을 넣었습니다. 또 실행 시각 대신 "마지막 실행 후 13시간 초과"를 멈춤 기준으로 바꿨습니다. 이 수정 뒤에는 실제 Claude로 다시 돌리지 않았습니다(테스트만 통과).
- 서버의 실제 계산 시간은 데이터 길이에 비례합니다. 3년치 5분봉이면 코인당 몇 분 걸릴 것으로 예상하며, 하루 두 번이라 문제없는 수준입니다(서버에서 확인 필요).

## 서버 설치
```bash
cd /opt/crypto-bot-research
sudo pip3 install -r requirements.txt          # numpy, pandas, scipy
# 1) 처음 한 번: 과거 3년치 받기 (공개 데이터, 키 불필요). 요청 간격을 둬서 수십 분 걸릴 수 있음
sudo -u paperbot python3 -m paperbot.record sync --market /var/lib/paperbot/market.db
# 2) 신호 계산 한 번
sudo -u paperbot python3 -m paperbot.record compute --market /var/lib/paperbot/market.db --ledger /var/lib/paperbot/paper.db
# 3) 상태 보기
sudo -u paperbot python3 -m paperbot.record status --market /var/lib/paperbot/market.db
# 4) 하루 두 번(09:10, 21:40 KST) 자동: 받기 + 계산
sudo cp deploy/paperbot-record.service deploy/paperbot-record.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now paperbot-record.timer
```
- 09:10은 일봉이 09:00 KST에 닫힌 직후이고, 21:40은 22:00 저녁 점검 직전입니다.
- 호가 스냅샷은 실시간 봇(`paperbot.live run`)이 돌고 있을 때만 쌓입니다.

2. **재시작 복구**: 관찰용 계좌가 포지션을 잡기 시작하면 꼭 필요합니다.

4. **재현 시험 3단계** (Astral 대 바이낸스).
5. **새 가설 데이터**: 백테스트 세션이 새 가설과 필요한 데이터 목록을 주면, 그중 나중에 받을 수 없는 것(예: 호가)부터 기록에 추가합니다.
